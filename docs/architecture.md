# Архитектура

Проект реализован как модульный монолит.

```text
Пользователь / Администратор
            ↓
        Vue 3 SPA
            ↓
       Go HTTP API
       ↙         ↘
PostgreSQL    Negotiation Engine
                    ↓ решение и базовая реплика
             Gemini / локальный ответ
```

## Frontend

Vue отвечает за интерфейс игрока и администратора. Состояние переговорной
сессии хранится в Pinia. Повторяемая логика выносится в composables, HTTP-вызовы
изолированы в `src/api`.

## Backend

- `httpapi` — HTTP-маршруты и middleware;
- `adminauth` — хеширование пароля и управление административными сессиями;
- `negotiation` — бизнес-логика и оценка реплик;
- `repository` — хранение сценариев и сессий;
- `llm` — абстракция AI-провайдера;
- `database` — подключение к PostgreSQL;
- `webapp` — встроенная production-сборка Vue.

## HTTP-конвейер

Входящий запрос проходит через middleware в следующем порядке:

```text
security headers → request ID → журналирование → rate limit → panic recovery → route
```

Panic recovery находится рядом с маршрутизатором, поэтому журнал запроса видит
фактический статус `500`. Публичный rate limit применяется только к изменяющим
запросам, а попытки административного входа ограничиваются отдельно. Таблица
клиентов лимитера имеет верхнюю границу и удаляет просроченные записи.

## Надёжность AI

Сценарный движок работает без внешней модели. Явные переговорные действия
сначала распознаёт локальный классификатор, чтобы результат не зависел от
вариативности модели. Для неоднозначного свободного текста Gemini возвращает
типизированную классификацию по JSON Schema: релевантность сценарию, одно
намерение из закрытого списка и, при наличии, параметры предложения. Backend
проверяет полученный `PlayerMove`, после чего сам изменяет состояние и очки,
формирует анализ и выбирает базовую реплику. Следующий вызов Gemini делает эту
реплику более естественной. Модель не возвращает числовые изменения показателей
и не может напрямую изменить решение движка.

Интеграция использует REST `generateContent`, ключ передаётся в заголовке
`x-goog-api-key`. HTTP-клиент имеет настраиваемый таймаут, ответ ограничен по
размеру и длине. Сетевая ошибка, ограничение квоты, блокировка или пустой ответ
при классификации переключают ход на локальный анализатор; ошибка генерации
ответа возвращает базовую детерминированную реплику. Для каждого состояния у
локального движка есть несколько смысловых формулировок. Номер хода выбирает
вариант воспроизводимо, а повтор действия получает отдельный ответ с указанием
следующего полезного шага. Ход при этом не отменяется.
Ошибочная конфигурация, например `LLM_PROVIDER=gemini` без ключа, останавливает
запуск с понятной ошибкой.

Ключи Gemini хранятся в пуле из 1–8 уникальных значений. Начальный ключ
выбирается циклически и безопасно для параллельных запросов. Ошибки авторизации,
доступа и квоты переключают запрос на следующий ключ; после исчерпания пула
действует обычный локальный fallback. Значения ключей не записываются в логи.
Ключ с исчерпанной квотой временно исключается с учётом `Retry-After`, а
отклонённый ключ — минимум на пять минут. Ошибки `500` и `503` повторяются один
раз перед локальным fallback.

## Правила сценария и состояние сессии

У сценария есть сохранённые в PostgreSQL правила: рекомендуемое число ходов,
порог доверия, необходимые действия и ограничения предложения собеседника. У сессии есть
отдельное состояние этапа переговоров и выполненных действий. Миграция
`00002` заполняет правила существующих демонстрационных сценариев; при первом
запуске на пустой БД эти правила задаёт `SeedDefaults()`.

Каждый ход получает объяснимый разбор: распознанную технику, изменения доверия,
аргументации и давления, сильные стороны, риски, стабильные коды ошибок и
рекомендацию. Разбор возвращается вместе с ответом и сохраняется как JSONB в
`messages.analysis` у реплики игрока.

При завершении сессии движок читает сохранённые разборы и формирует сводку:
частоту техник, классы ошибок с тяжестью и номерами ходов, повторяющиеся риски,
приоритетные рекомендации и лучший ход. Текст риска остаётся пояснением для
человека, а код ошибки служит стабильным контрактом для интерфейса, достижений
и аналитики. Сводка сохраняется в `results.analysis`, поэтому результат после
перезапуска сервера совпадает с результатом, полученным при завершении
переговоров.

После итоговой оценки детерминированный модуль достижений проверяет исход,
состояние сессии, классы ошибок и происхождение ветки. Открытые достижения
сохраняются в `results.achievements`; публичный каталог доступен без обращения
к базе.

Локальный профиль игрока хранит счётчики завершённых и успешных сессий,
текущую и лучшую серии, открытый уровень сложности и уникальные достижения.
Сессия может ссылаться на профиль через `player_id`; дочерняя ветка наследует
эту ссылку. При завершении репозиторий одной транзакцией сохраняет результат,
обновляет прогресс и добавляет новые строки в `player_achievements`. Повторный
`finish` не меняет счётчики, поскольку завершённая сессия читает уже
сохранённый результат.

Первая реплика копируется в сессию при её создании. Поэтому последующее
редактирование сценария не изменяет историю уже начатых переговоров.

Публичный список сценариев не возвращает правила и цель собеседника. Файлы в
`scenarios/` служат примерами данных: сервер сейчас заполняет демонстрационные
сценарии в `SeedDefaults()`. Движок применяет правила к проверке ходов,
изменению состояния переговоров и итоговой оценке.

Структурированный движок поддерживает Гарвардский метод, четыре этапа SPIN и
подготовку BATNA. Прогресс SPIN и факт определения BATNA хранятся во флагах
`SessionState` внутри JSONB `negotiation_sessions.state`; поле `spinStage`
фиксирует последний последовательно завершённый этап. Старые записи остаются
совместимыми: отсутствующие флаги читаются как `false`. Нарушение порядка SPIN
не блокирует ход, но уменьшает его влияние и отражается в объяснимом разборе.

Скрытая модель оппонента хранится в правилах сценария. Она задаёт минимальный
уровень аргументации, допустимое давление, предпочтительное предложение и
жёсткий предел уступки. Техническая граница ввода отделена от предела уступки:
движок может принять корректно сформированное, но неприемлемое предложение,
дать встречную границу и завершить сессию исходом `walk_away`. Результат хранит
стабильный `outcomeCode` вместе с текстовым описанием.

Режим сложного клиента расширяет правила объектом `behavior`. Движок по номеру
хода рассчитывает настроение, дополнительное изменение доверия и смену
приоритета. Расчёт не использует случайность: одинаковая контрольная точка и
одинаковый ход всегда дают одинаковую реакцию. Текущее настроение, приоритет и
число применённых смен сохраняются в `SessionState`, а описание реакции — в
`messages.analysis.opponentReaction`. Поэтому ветвление не нарушает
воспроизводимость переговоров.

Принятие допустимого предложения автоматически переводит сессию в `finished` и
сохраняет результат. Число `maxTurns` не обрывает активный диалог: пользователь
может продолжать его, завершить вручную или прервать со статусом `abandoned`.
Повторные запросы завершения читают уже сохранённый результат, поэтому клиент
может безопасно повторить запрос после сетевой ошибки. Запись терминального
статуса и результата выполняется одной транзакцией репозитория.

При создании сессии сохраняется начальная контрольная точка. Каждый следующий
ход атомарно обновляет сессию, добавляет реплики и записывает состояние после
хода в `session_checkpoints`.

Откат реализован как новая ветка: репозиторий одной транзакцией создаёт
активную дочернюю сессию, копирует реплики и контрольные точки до выбранного
хода и восстанавливает сохранённое состояние. Поля `parent_session_id` и
`forked_from_turn` сохраняют происхождение ветки. Исходная сессия и её история
не изменяются.

Административный API возвращает полную модель сценария и позволяет создавать,
изменять и удалять сценарии. Изменение блокируется при активных переговорах.
Удаление блокируется при наличии любой связанной сессии, поэтому история и
результаты переговоров не теряют ссылку на исходный сценарий.

Административная история читает сессии постранично и фильтрует их по статусу и
сценарию. Детальная запись объединяет снимок состояния, полный сценарий,
сообщения с анализами и сохранённый результат. Агрегированная статистика
считает статусы, средний балл и распределение исходов непосредственно в
репозитории, чтобы не загружать всю историю в память приложения.

## Production

Vue собирается на первом этапе Dockerfile. Результат встраивается в Go-бинарник.
В production запускается один контейнер и управляемая PostgreSQL. Финальный
образ работает от непривилегированного пользователя. `.dockerignore` исключает
`.env`, Git, локальные сборочные кэши, `node_modules` и готовые frontend-артефакты
из build context.

Запуск имеет общий 30-секундный контекст для подключения к БД, миграций,
заполнения демонстрационных сценариев и инициализации администратора. HTTP
сервер использует отдельные таймауты чтения заголовков, чтения тела, записи и
idle-соединения. `SIGINT` и `SIGTERM` запускают graceful shutdown с таймаутом
10 секунд.

В режиме `APP_ENV=production` обязательны PostgreSQL и пароль администратора
длиной не менее 12 символов, отличный от значения по умолчанию.

## Авторизация администратора

При запуске пароль администратора из окружения хешируется bcrypt и сохраняется
в PostgreSQL. После входа сервер выдаёт случайный токен с ограниченным сроком
действия. В базе хранится только SHA-256 hash токена. Смена настроенного пароля
и `POST /api/v1/admin/logout` отзывают активные сессии. Просроченные записи
удаляются при запуске и успешном входе. Число попыток входа ограничено временным
окном.

HTTP слой добавляет Content Security Policy, запрет встраивания страницы,
запрет MIME sniffing, ограничение browser permissions и строгую referrer policy.
Каждый ответ получает случайный request ID, а структурированный JSON-журнал
содержит метод, путь, статус, объём ответа и длительность. Заголовок
`X-Forwarded-For` влияет на rate limit только при явном
`TRUST_PROXY_HEADERS=true`.
