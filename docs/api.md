# API

## Сценарии

- `GET /api/v1/scenarios` — публичный список сценариев без правил и цели собеседника;
  поле `opponentMode` имеет значение `standard` или `difficult`.
- `GET /api/v1/admin/scenarios` — полный список для администратора, включая
  правила и скрытую цель собеседника.
- `POST /api/v1/admin/scenarios` — создание сценария.
- `PUT /api/v1/admin/scenarios/{id}` — полная замена сценария.
- `DELETE /api/v1/admin/scenarios/{id}` — удаление сценария.

Все маршруты `/api/v1/admin/scenarios` требуют Bearer token. Повторный `id`
при создании возвращает `409 Conflict`. Сценарий нельзя изменить, пока у него
есть активная сессия, и нельзя удалить, если с ним связана любая сессия.

При создании сценария обязательны `title`, `sphere`, `topic`, `difficulty`,
`opponentRole`, `opponentTone`, `playerGoal`, `opponentGoal` и `initialMessage`.
Допустимые значения `difficulty`: `easy`, `medium`, `hard`. Строки очищаются от
пробелов по краям, а если `id` не передан, сервер создаёт его из названия.

Поле `rules` можно не передавать: сервер применит стандартные правила. Если
правила переданы, сервер проверяет лимит ходов, порог доверия, веса оценки,
ограничение предложения и уникальность альтернатив. Некорректный сценарий
возвращает `400 Bad Request` и не сохраняется.

Для отдельного режима сложного клиента в `rules.behavior` задаются
эмоциональность, волатильность, исходный приоритет и расписание его изменений:

```json
{
  "mode": "difficult",
  "emotionality": 2,
  "volatility": 2,
  "initialPriority": "соблюдение срока",
  "priorityShifts": [
    {"turn": 3, "priority": "снижение рисков"},
    {"turn": 6, "priority": "поэтапная поставка"}
  ]
}
```

`emotionality` и `volatility` принимают значения от 1 до 3. Ходы смены
приоритетов должны идти по возрастанию и не превышать `maxTurns`. У стандартного
оппонента эти настройки отсутствуют.

## Профиль игрока

- `POST /api/v1/players` — создать локальный профиль игрока;
- `GET /api/v1/players/{id}` — получить прогресс, серию и накопленные достижения.

При создании можно передать имя длиной до 50 символов:

```json
{
  "displayName": "Алекс"
}
```

Пустое имя заменяется на `Игрок`. Новый профиль получает уровень `easy`.
После двух успешных сессий открывается `medium`, после пяти — `hard`.
Успешными считаются исходы `mutual_gain`, `advantageous_agreement` и
`compromise`. Неуспешное завершение сбрасывает `currentWinStreak`, но не
уменьшает `bestWinStreak`, число успешных сессий и уже открытые достижения.

Профиль пока локальный и не использует регистрацию: его `id` клиент должен
сохранить, например в local storage.

## Сессии

- `GET /api/v1/achievements` — получить каталог достижений и условия открытия.
- `POST /api/v1/sessions` — запустить сессию.
- `GET /api/v1/sessions/{id}` — получить состояние, включая этап переговоров.
- `GET /api/v1/sessions/{id}/messages` — получить историю реплик.
- `GET /api/v1/sessions/{id}/checkpoints` — получить сохранённые состояния ходов.
- `POST /api/v1/sessions/{id}/fork` — создать новую ветку с выбранного хода.
- `POST /api/v1/sessions/{id}/messages` — отправить реплику и структурированное намерение игрока.
- `POST /api/v1/sessions/{id}/finish` — завершить переговоры.
- `POST /api/v1/sessions/{id}/abandon` — прервать переговоры.
- `GET /api/v1/sessions/{id}/result` — получить итог.

Для запуска с учётом прогрессии передаётся `playerId`:

```json
{
  "scenarioId": "vendor-introduction",
  "playerId": "идентификатор профиля"
}
```

Если сложность сценария ещё не открыта, сервер возвращает `403 Forbidden`.
Запуск без `playerId` остаётся доступен для совместимости и не изменяет
прогресс какого-либо игрока. Дочерняя ветка наследует `playerId` исходной
сессии.

`finish` и `abandon` идемпотентны: если результат уже сформирован, повторный
запрос возвращает сохранённый результат без повторного расчёта. После ручного
прерывания сессия получает статус `abandoned`, а результат — код `abandoned`.

Контрольная точка `turn: 0` соответствует началу переговоров. После каждого
хода сохраняются номер хода, три показателя, полный `SessionState` и время.
Контрольная точка и две реплики хода записываются одной транзакцией.

### Новая ветка сессии

Чтобы повторить переговоры с выбранного момента, клиент отправляет номер
сохранённой контрольной точки:

```json
{
  "turn": 2
}
```

`POST /api/v1/sessions/{id}/fork` возвращает новую активную сессию со статусом
`201 Created`. Сервер копирует в неё начальную реплику и все пары реплик до
указанного хода, восстанавливает показатели и `SessionState`. Исходная сессия
не изменяется и может иметь любой статус.

В ответе новой сессии поля `parentSessionId` и `forkedFromTurn` указывают на
исходную ветку и точку ответвления. Номер хода должен соответствовать
существующей контрольной точке и быть меньше `rules.maxTurns`, иначе сервер
возвращает `400 Bad Request`.

### Ход игрока

Допустимые `intent`:

- Гарвардский метод: `ask_interest`, `present_evidence`, `propose`, `accept`;
- SPIN: `ask_situation`, `identify_problem`, `explore_implication`,
  `clarify_need_payoff`;
- подготовка альтернативы: `state_batna`;
- конкурентное давление: `pressure`.

Длина `content` ограничена 4000 символами. API принимает ровно один JSON-объект
и отклоняет неизвестные поля.

Обычный ход:

```json
{
  "content": "Какие условия для вас важны?",
  "intent": "ask_interest"
}
```

Числовое предложение:

```json
{
  "content": "Предлагаю повышение на 7%",
  "intent": "propose",
  "proposal": {
    "kind": "raise_percent",
    "value": 7
  }
}
```

У числового ограничения сценария есть три скрытых порога:

- `preferredValue` — предпочтительное для оппонента значение;
- `maximumValue` — последний приемлемый предел уступки;
- `inputMaximumValue` — только техническая граница входного значения.

Поэтому предложение между `maximumValue` и `inputMaximumValue` считается
корректным запросом, но оппонент его отклоняет и сообщает допустимый предел.
Подтвердить отклонённое предложение ходом `accept` нельзя. Для именованных
альтернатив аналогичную роль выполняют `preferredAlternativeIds`.

Предложение из сценарных альтернатив:

```json
{
  "content": "Вернёмся к вопросу через три месяца",
  "intent": "propose",
  "proposal": {
    "alternativeId": "review_in_3_months"
  }
}
```

Для сценария со стандартным `proposal.kind: "none"` можно сделать свободное
предложение без объекта `proposal`:

```json
{
  "content": "Предлагаю разбить работу на два этапа и согласовать контрольные точки",
  "intent": "propose"
}
```

Для совместимости запрос только с `content` пока обрабатывается прежним mock-анализатором. Структурированный ход изменяет этап, флаги сессии и очки по детерминированным правилам. Ответ оппонента для такого хода также выбирается детерминированно: он учитывает обязательные условия сценария и текущий уровень доверия, не вызывая legacy provider.

SPIN-ходы лучше отправлять последовательно: ситуация, проблема, последствия,
ценность решения. Сервер разрешает другой порядок, но снижает эффект хода и
добавляет риск с рекомендацией в `analysis`. `state_batna` фиксирует, что игрок
определил лучшую альтернативу на случай отсутствия соглашения. Содержимое
альтернативы передаётся в `content` и остаётся частью истории переговоров.

Ответ на ход содержит объект `analysis`:

```json
{
  "reply": "Для меня важно снизить риски...",
  "session": {},
  "analysis": {
    "intent": "ask_interest",
    "technique": "harvard_interests",
    "trustDelta": 2,
    "argumentDelta": 0,
    "pressureDelta": 0,
    "summary": "Вы исследовали интересы второй стороны и укрепили доверие.",
    "strengths": ["Открытый вопрос помогает перейти от позиций к интересам"],
    "risks": [],
    "errors": [],
    "opponentReaction": {
      "mood": "receptive",
      "priority": "снижение рисков",
      "priorityChanged": false,
      "trustDelta": 1
    },
    "recommendation": "После уточнения интересов подкрепите позицию измеримыми фактами."
  }
}
```

`opponentReaction` присутствует в режиме `difficult`. Поле показывает текущее
настроение, приоритет, факт его изменения и дополнительное влияние поведения
клиента на доверие. Давление сильнее снижает доверие эмоционального клиента,
вопрос после раздражения помогает снизить напряжение, а волатильность вызывает
скептическую реакцию на детерминированных ходах. Настроение и приоритет входят
в `SessionState`, поэтому откат точно воспроизводит дальнейшее поведение.

Когда ход исчерпывает `rules.maxTurns`, сервер автоматически завершает сессию.
В этом случае `session.status` в ответе равен `finished`, а рядом с `analysis`
возвращается поле `result` с итогом переговоров. В промежуточных ходах поле
`result` отсутствует.

Тот же объект сохраняется в поле `analysis` соответствующей реплики игрока и
возвращается через `GET /api/v1/sessions/{id}/messages`. У реплик оппонента это
поле отсутствует. Основные коды техник: `harvard_interests`,
`evidence_based_argument`, `harvard_mutual_gain`, `agreement_confirmation`,
`competitive_pressure`.

Для SPIN и BATNA используются коды `spin_situation`, `spin_problem`,
`spin_implication`, `spin_need_payoff` и `batna_preparation`.

Поле `errors` содержит машиночитаемые ошибки конкретного хода. У каждой ошибки
есть стабильный `code`, короткий `label`, тяжесть `severity` (`low`, `medium`,
`high` или `critical`) и пояснение `message`. Сейчас движок распознаёт коды:

- `evidence_before_interests`;
- `spin_problem_before_situation`;
- `spin_implication_before_problem`;
- `spin_need_payoff_before_implication`;
- `batna_before_interests`;
- `proposal_before_interests`;
- `proposal_without_evidence`;
- `proposal_outside_limit`;
- `pressure_tactic`.

### Итог переговоров

Для структурированной сессии соглашение требует сделанного и принятого предложения, достаточного доверия и выполнения обязательных условий сценария: исследования интересов и представления доказательств. Итоговый балл учитывает веса доверия, аргументации и давления из правил сценария. Ответ содержит объяснимые сильные стороны, ошибки и рекомендации.

Поле `achievements` результата содержит достижения, открытые в этой сессии.
Каталог и порядок кодов стабильны:

- `first_round` — завершена сессия хотя бы с одним ходом;
- `deal_maker` — достигнуто устойчивое соглашение;
- `mutual_benefit` — получен исход `mutual_gain`;
- `calm_negotiator` — устойчивое соглашение достигнуто без давления;
- `well_prepared` — исследованы интересы, представлены доказательства и определена BATNA;
- `spin_master` — последовательно пройдены четыре этапа SPIN;
- `clean_run` — в завершённой сессии нет классифицированных ошибок;
- `successful_replay` — устойчивое соглашение достигнуто в дочерней ветке;
- `difficult_client` — устойчивое соглашение достигнуто со сложным клиентом.

Достижения сохраняются вместе с результатом и не пересчитываются при повторном
`finish`. Если сессия связана с профилем, новые достижения атомарно добавляются
в его коллекцию без дублей.

Машиночитаемое поле `outcomeCode` различает исходы:

- `mutual_gain` — взаимовыгодное соглашение в предпочтительном диапазоне;
- `advantageous_agreement` — выгодное соглашение;
- `compromise` — приемлемый компромисс;
- `fragile_agreement` — условия формально приняты без выполнения важных требований;
- `walk_away` — превышен предел уступки или допустимое давление;
- `no_agreement` — предложение не было сделано или принято.
- `abandoned` — игрок прервал сессию.

Скрытые правила `minimumArgumentScoreForAgreement` и
`maximumPressureForAgreement` задают минимальную аргументацию и предел давления
для конкретного оппонента. Они доступны только в административной модели
сценария и не возвращаются публичным списком.

Поле `analysis` объединяет разборы всех ходов игрока:

```json
{
  "analyzedTurns": 4,
  "techniques": [
    {
      "technique": "harvard_interests",
      "label": "Исследование интересов",
      "count": 2
    }
  ],
  "errorClasses": [
    {
      "code": "proposal_before_interests",
      "label": "Преждевременное предложение",
      "severity": "high",
      "count": 2,
      "turns": [1, 3]
    }
  ],
  "repeatedRisks": [
    {
      "risk": "Предложение сделано до исследования интересов",
      "count": 2
    }
  ],
  "priorityRecommendations": [
    "Уточните интересы собеседника и свяжите факты с его задачами."
  ],
  "bestMove": {
    "turn": 2,
    "technique": "evidence_based_argument",
    "label": "Аргументация фактами",
    "summary": "Вы усилили позицию фактами и конкретными аргументами.",
    "scoreImpact": 5
  }
}
```

`errorClasses` группирует ошибки по коду, возвращает число повторений и номера
ходов. Сначала идут более тяжёлые ошибки, затем более частые. Техники сортируются
по частоте, а текстовые риски попадают в итог, если встретились не менее двух
раз. В `priorityRecommendations` возвращаются до трёх наиболее частых
рекомендаций. Лучший ход определяется по влиянию на доверие, аргументацию и
давление; при равенстве выбирается более ранний ход.

Сессии, отправляющие только `content`, временно используют прежнюю оценку результата по баллам. Этот режим нужен для совместимости с текущим интерфейсом и будет удалён после перевода frontend на структурированные ходы.

## Администратор

- `POST /api/v1/admin/login` — получить случайный токен и время его истечения
  в поле `expiresAt`.
- `POST /api/v1/admin/logout` — отозвать текущий Bearer token.
- `GET /api/v1/admin/sessions` — история сессий с пагинацией;
- `GET /api/v1/admin/sessions/{id}` — сессия, сценарий, сообщения, контрольные точки и результат;
- `GET /api/v1/admin/session-statistics` — агрегированная статистика.

История поддерживает параметры `status`, `scenarioId`, `limit` и `offset`.
Допустимые статусы: `active`, `finished`, `abandoned`. Размер страницы по
умолчанию равен 20 и ограничен 100 записями. Ответ содержит `items`, `total`,
`limit` и `offset`.

Статистику можно ограничить параметром `scenarioId`. Она содержит количество
активных, завершённых и прерванных сессий, средний итоговый балл и распределение
по `outcomeCode`. Все endpoints истории требуют административный Bearer token.

Время жизни токена задаётся переменной `ADMIN_SESSION_TTL`, по умолчанию `12h`.
Пароль хранится в PostgreSQL только как bcrypt hash, а токен — как SHA-256 hash.
После пяти попыток вход временно блокируется на 15 минут. При блокировке API
возвращает `429 Too Many Requests` и заголовок `Retry-After`. Значения можно
изменить через `ADMIN_LOGIN_MAX_ATTEMPTS` и `ADMIN_LOGIN_WINDOW`.
