# API

## Сценарии

- `GET /api/v1/scenarios` — публичный список сценариев без правил и цели собеседника.
- `GET /api/v1/admin/scenarios` — полный список для администратора, включая
  правила и скрытую цель собеседника.
- `POST /api/v1/admin/scenarios` — создание сценария.
- `PUT /api/v1/admin/scenarios/{id}` — полная замена сценария.
- `DELETE /api/v1/admin/scenarios/{id}` — удаление сценария.

Все маршруты `/api/v1/admin/scenarios` требуют Bearer token. Повторный `id`
при создании возвращает `409 Conflict`. Сценарий нельзя изменить, пока у него
есть активная сессия, и нельзя удалить, если с ним связана любая сессия.

При создании сценария обязательны `title`, `sphere`, `topic`, `difficulty`,
`opponentRole`, `opponentTone`, `playerGoal`, `opponentGoal` и `initialMessage`.
Допустимые значения `difficulty`: `easy`, `medium`, `hard`. Строки очищаются от
пробелов по краям, а если `id` не передан, сервер создаёт его из названия.

Поле `rules` можно не передавать: сервер применит стандартные правила. Если
правила переданы, сервер проверяет лимит ходов, порог доверия, веса оценки,
ограничение предложения и уникальность альтернатив. Некорректный сценарий
возвращает `400 Bad Request` и не сохраняется.

## Сессии

- `POST /api/v1/sessions` — запустить сессию.
- `GET /api/v1/sessions/{id}` — получить состояние, включая этап переговоров.
- `GET /api/v1/sessions/{id}/messages` — получить историю реплик.
- `POST /api/v1/sessions/{id}/messages` — отправить реплику и структурированное намерение игрока.
- `POST /api/v1/sessions/{id}/finish` — завершить переговоры.
- `GET /api/v1/sessions/{id}/result` — получить итог.

### Ход игрока

Допустимые `intent`:

- Гарвардский метод: `ask_interest`, `present_evidence`, `propose`, `accept`;
- SPIN: `ask_situation`, `identify_problem`, `explore_implication`,
  `clarify_need_payoff`;
- подготовка альтернативы: `state_batna`;
- конкурентное давление: `pressure`.

Длина `content` ограничена 4000 символами. API принимает ровно один JSON-объект
и отклоняет неизвестные поля.

Обычный ход:

```json
{
  "content": "Какие условия для вас важны?",
  "intent": "ask_interest"
}
```

Числовое предложение:

```json
{
  "content": "Предлагаю повышение на 7%",
  "intent": "propose",
  "proposal": {
    "kind": "raise_percent",
    "value": 7
  }
}
```

Предложение из сценарных альтернатив:

```json
{
  "content": "Вернёмся к вопросу через три месяца",
  "intent": "propose",
  "proposal": {
    "alternativeId": "review_in_3_months"
  }
}
```

Для сценария со стандартным `proposal.kind: "none"` можно сделать свободное
предложение без объекта `proposal`:

```json
{
  "content": "Предлагаю разбить работу на два этапа и согласовать контрольные точки",
  "intent": "propose"
}
```

Для совместимости запрос только с `content` пока обрабатывается прежним mock-анализатором. Структурированный ход изменяет этап, флаги сессии и очки по детерминированным правилам. Ответ оппонента для такого хода также выбирается детерминированно: он учитывает обязательные условия сценария и текущий уровень доверия, не вызывая legacy provider.

SPIN-ходы лучше отправлять последовательно: ситуация, проблема, последствия,
ценность решения. Сервер разрешает другой порядок, но снижает эффект хода и
добавляет риск с рекомендацией в `analysis`. `state_batna` фиксирует, что игрок
определил лучшую альтернативу на случай отсутствия соглашения. Содержимое
альтернативы передаётся в `content` и остаётся частью истории переговоров.

Ответ на ход содержит объект `analysis`:

```json
{
  "reply": "Для меня важно снизить риски...",
  "session": {},
  "analysis": {
    "intent": "ask_interest",
    "technique": "harvard_interests",
    "trustDelta": 2,
    "argumentDelta": 0,
    "pressureDelta": 0,
    "summary": "Вы исследовали интересы второй стороны и укрепили доверие.",
    "strengths": ["Открытый вопрос помогает перейти от позиций к интересам"],
    "risks": [],
    "recommendation": "После уточнения интересов подкрепите позицию измеримыми фактами."
  }
}
```

Тот же объект сохраняется в поле `analysis` соответствующей реплики игрока и
возвращается через `GET /api/v1/sessions/{id}/messages`. У реплик оппонента это
поле отсутствует. Основные коды техник: `harvard_interests`,
`evidence_based_argument`, `harvard_mutual_gain`, `agreement_confirmation`,
`competitive_pressure`.

Для SPIN и BATNA используются коды `spin_situation`, `spin_problem`,
`spin_implication`, `spin_need_payoff` и `batna_preparation`.

### Итог переговоров

Для структурированной сессии соглашение требует сделанного и принятого предложения, достаточного доверия и выполнения обязательных условий сценария: исследования интересов и представления доказательств. Итоговый балл учитывает веса доверия, аргументации и давления из правил сценария. Ответ содержит объяснимые сильные стороны, ошибки и рекомендации.

Поле `analysis` объединяет разборы всех ходов игрока:

```json
{
  "analyzedTurns": 4,
  "techniques": [
    {
      "technique": "harvard_interests",
      "label": "Исследование интересов",
      "count": 2
    }
  ],
  "repeatedRisks": [
    {
      "risk": "Предложение сделано до исследования интересов",
      "count": 2
    }
  ],
  "priorityRecommendations": [
    "Уточните интересы собеседника и свяжите факты с его задачами."
  ],
  "bestMove": {
    "turn": 2,
    "technique": "evidence_based_argument",
    "label": "Аргументация фактами",
    "summary": "Вы усилили позицию фактами и конкретными аргументами.",
    "scoreImpact": 5
  }
}
```

Техники сортируются по частоте, а риски попадают в итог, если встретились не
менее двух раз. В `priorityRecommendations` возвращаются до трёх наиболее
частых рекомендаций. Лучший ход определяется по влиянию на доверие,
аргументацию и давление; при равенстве выбирается более ранний ход.

Сессии, отправляющие только `content`, временно используют прежнюю оценку результата по баллам. Этот режим нужен для совместимости с текущим интерфейсом и будет удалён после перевода frontend на структурированные ходы.

## Администратор

- `POST /api/v1/admin/login` — получить случайный токен и время его истечения
  в поле `expiresAt`.
- `POST /api/v1/admin/logout` — отозвать текущий Bearer token.

Время жизни токена задаётся переменной `ADMIN_SESSION_TTL`, по умолчанию `12h`.
Пароль хранится в PostgreSQL только как bcrypt hash, а токен — как SHA-256 hash.
После пяти попыток вход временно блокируется на 15 минут. При блокировке API
возвращает `429 Too Many Requests` и заголовок `Retry-After`. Значения можно
изменить через `ADMIN_LOGIN_MAX_ATTEMPTS` и `ADMIN_LOGIN_WINDOW`.
